## [2026-11-12] 장르 원-핫 설계 시 "기타" 버킷 주의

**Trigger**: "미분류를 제외한 메인 후보 중에 사용자의 취향과 맞지않는 군집이 생기는 경우는
없는지 한번 봐줄래" — 직접 조사해보니 실제로 "스포츠/기타"가 서커스/마술·연극·대중무용·
전통무용을 뭉친 잡동사니 버킷이었고, 그 안에서 완전히 무관한 두 공연(마술 vs 연극)이 장르
원-핫만으로 코사인 유사도 0.5를 받고 있었음.
**Pattern**: 장르 원-핫 인코딩을 만들 때, "미분류"처럼 명시적인 캐치올 버킷은 신경 썼지만
"기타"라는 이름이 붙은 **또 다른 캐치올**은 "정식 장르 중 하나"로 착각해 그대로 원-핫에
넣었다. 이름에 "기타/etc/other"가 들어간 범주는, 실제로는 "같은 종류"라는 의미를 갖지 않는
이질적인 항목들의 집합이라는 걸 놓친 것.
**Rule**: 분류 체계에 "기타"류 캐치올 버킷이 있으면, 그걸 원-핫·클러스터링 등 "같은 값 =
비슷함"을 가정하는 특성으로 쓰기 전에 그 버킷 안에 실제로 뭐가 섞여 있는지 원본 데이터로
먼저 확인한다. 이질적이면 그 범주는 유사도 계산에서 신호를 주지 않거나(텍스트 등 다른
신호에만 맡기거나), 세부 카테고리로 더 쪼갠다.
**Files affected**: `recommender/vectorize.py`(`NO_GENRE_SIGNAL`), 그리고 앞으로 장르·
카테고리형 특성을 원-핫/벡터화하는 모든 코드.


## [2026-11-12] 수집 스크립트는 "부분 실패"를 "성공"처럼 저장하면 안 된다

**Trigger**: 사용자가 요청한 재수집(`pipeline/collection`)을 실행했는데, KOPIS 쪽 요청이
일시적으로 대량 실패(9건 실패 → 259건 실패)했음에도 `collect_kopis.py`가 그 적은 결과를
그대로 `performance_detail.json`에 저장해버려 812건 → 565건으로 **247건을 손상**시켰다.
같은 세션에서 `collect_kopis_boxoffice.py`도 똑같은 패턴으로 600건짜리 데이터를 빈
배열(`[]`)로 덮어쓴 적이 있었다(먼저 발견해서 그건 고쳐뒀었는데, 같은 버그가 다른
스크립트에도 있다는 걸 놓쳤다).
**Pattern**: "여러 건을 하나씩 가져와서 실패한 건 건너뛰고 계속 진행한 뒤, 끝나면 모은
결과를 무조건 저장한다"는 코드 패턴은 — 외부 API가 일시적으로 불안정해지는 순간 "적게
수집된 결과"를 "완전한 최신 데이터"처럼 그대로 덮어써버린다. `data/raw` 원본을 손상시키지
않는다는 규칙이 있었는데도, 수집 스크립트 자체의 저장 로직까지는 그 규칙을 적용하지
않았던 것.
**Rule**: 여러 건을 개별적으로 가져오면서 **일부 실패를 허용(catch-and-continue)하는
수집·동기화 스크립트는, 저장 직전에 반드시 "실패분을 기존 저장 데이터로 보존(merge)"하거나
"결과가 비정상적으로 적으면 저장을 중단"하는 안전장치를 넣는다.** 단일 호출로 전부
성공/실패가 갈리는 스크립트(실패 시 예외가 저장 전에 터지는 구조)는 이미 안전하므로
해당 없음 — 캐치-앤-컨티뉴 패턴이 있는 곳만 확인하면 된다.
**Files affected**: `pipeline/collection/collect_kopis.py`(수정함 — mt20id별로 기존 데이터와
merge), `collect_kopis_boxoffice.py`(수정함 — 전부 실패 시 저장 안 함). 앞으로 비슷한
캐치-앤-컨티뉴 구조의 수집 스크립트를 새로 만들 때도 적용할 것.

## [2026-11-12] 신호를 죽인 특성은 프로필/쿼리 쪽에서도 똑같이 죽여야 한다

**Trigger**: 사용자가 "장르를 다른 걸 선택했는데 계속 똑같은 공연이 나오는 오류는
없었냐"고 물어서 6개 장르를 직접 비교해봤더니, "스포츠/기타"를 고르면 "콘서트"와
완전히 똑같은 결과가 나오는 버그를 발견했다.
**Pattern**: `vectorize.py`에서 "스포츠/기타"(잡동사니 장르)의 원-핫 신호를 0으로
죽였는데, 그 사실을 `build_profile_vector`(사용자 취향 벡터를 만드는 쪽)에는 반영하지
않았다. 데이터 쪽 특성 하나를 "신호 없음"으로 바꾸면, 그 특성을 참조하는 다른 모든
곳(쿼리·프로필 생성 등)도 똑같이 바꿔야 하는데, 한쪽만 고치고 반대쪽(사용자 입력을
벡터로 바꾸는 코드)은 안 고쳐서 생긴 불일치였다. 결과적으로 "신호가 없다"가 아니라
"신호가 0이라 조용히 인기도 순위로 대체"되는, 겉으로는 티가 안 나는 버그가 됐다.
**Rule**: 벡터의 어떤 차원(장르·태그 등)을 "쓰지 않기로" 결정하면, 그 벡터를 만드는
모든 경로(공연 쪽 인코딩 + 사용자 프로필/쿼리 쪽 인코딩)를 한 번에 검토해서 똑같이
반영한다. 수정 직후엔 "같은 특성의 다른 값들을 넣었을 때 결과가 실제로 달라지는지"를
항목별로 직접 비교해 확인한다(이번처럼 "장르를 바꿔가며 결과 비교"하는 것).
**Files affected**: `recommender/vectorize.py`(`NO_GENRE_SIGNAL` 정의)와
`recommender/recommend.py`(`build_profile_vector`) — 둘이 항상 같은 기준을 참조해야
한다. 앞으로 벡터의 특성을 추가/제거할 때도 이 양쪽을 함께 확인할 것.

## [2026-11-12] 환경 제약을 "불가능"으로 단정하기 전에 타임아웃을 먼저 늘려봐야 한다

**Trigger**: 백엔드 단계에서 uvicorn을 띄우고 짧게(5~10초) 기다렸다가 curl이 실패하자
"이 샌드박스는 포트를 리스닝하는 백그라운드 프로세스를 두면 세션이 강제 종료된다"고
결론 내리고 `backend/README.md`에 그대로 적어뒀다. 나중에(`/run` 스킬이 알려준 "포트를
`lsof`로 비우고, `sleep` 대신 길게 폴링하라"는 패턴을 따라) 똑같은 명령을 40초 넘게
기다려보니 **정상적으로 떴다** — 진짜 원인은 WSL의 `/mnt/c/...` 경로라 pandas 등 무거운
import의 콜드 스타트가 느렸던 것뿐이었다(디스크 I/O 대기).
**Pattern**: 실행 결과가 기대와 다르게 "실패"로 보일 때, 몇 번 짧게 재시도해보고 바로
"환경이 이걸 지원하지 않는다"는 결론으로 건너뛰었다. 실제로는 "아직 안 끝났을 뿐"이었는데,
그 가능성(느린 콜드 스타트, 디스크 I/O)을 먼저 배제하지 않고 더 근본적인(그리고 더
비관적인) 원인으로 단정해버렸다. 그 결론을 문서에 "사실"로 적어두기까지 해서, 나중에
다시 확인하지 않았다면 계속 틀린 정보로 남을 뻔했다.
**Rule**: 실행이 "실패"처럼 보이면, 환경 제약으로 결론 내리기 전에 (1) 프로세스가
실제로 살아있는지(`ps aux`) 먼저 확인하고, (2) 살아있다면 타임아웃을 몇 배로 늘려
재시도한다. 특히 WSL의 윈도우 드라이브 경로(`/mnt/c/...`)처럼 디스크 I/O가 느릴 수 있는
환경에서는 "무거운 라이브러리 import + 첫 실행"은 수십 초가 걸릴 수 있다는 걸 기본으로
가정한다. 불확실한 원인 추정을 문서에 "사실"로 적을 때는 "~인 것으로 보임/추정" 같은
표현을 쓰고, 나중에 반증되면 바로 정정한다(이번처럼 취소선으로 표시).
**Files affected**: 로컬에서 서버·데몬을 띄우고 폴링하는 모든 작업(`backend/README.md`,
`frontend/README.md`에 정정 반영함). 앞으로 비슷한 "안 뜬다"류 증상을 보면 이 교훈부터
먼저 떠올릴 것.

## [2026-11-12] API 단위 테스트가 통과해도 실제 브라우저로 한 번은 때려봐야 한다

**Trigger**: 백엔드는 `TestClient`로 8개 엔드포인트를 전부 통과시켜놓고 "검증 완료"라고
보고했는데, 사용자가 sudo로 Playwright 의존성을 설치해준 뒤 실제 Chromium으로 띄워보니
**프론트엔드가 아예 동작하지 않았다**(CORS 미설정 + Next.js `allowedDevOrigins` 차단,
둘 다 실제 브라우저가 아니면 절대 드러나지 않는 종류의 버그).
**Pattern**: `fastapi.testclient.TestClient`는 ASGI 앱을 "실제 네트워크·브라우저 보안
정책 없이" 직접 호출하는 테스트 도구라서, CORS·쿠키·Origin 체크처럼 **브라우저가 강제하는
규칙은 아예 검사 대상에서 빠진다**. "API가 Postman/TestClient로 통과했다"를 "프론트엔드와
실제로 연동된다"와 동일시한 게 착오였다.
**Rule**: 프론트엔드와 백엔드가 다른 origin(포트 포함)으로 통신하는 구조라면, API 단위
테스트와는 별개로 **실제 브라우저(또는 최소한 브라우저의 fetch 의미론을 지키는 도구)로
한 번은 끝까지 연동 테스트**를 해야 한다. 특히: (1) CORS 미들웨어가 있는지, (2) 프레임워크의
dev 서버가 접근 호스트(localhost vs 127.0.0.1 등)를 기본 차단하지 않는지 먼저 의심한다.
**Files affected**: `backend/main.py`(CORSMiddleware), `frontend/next.config.ts`
(allowedDevOrigins). 앞으로 프론트+백엔드를 분리 포트로 구성하는 모든 프로젝트에 적용.

## [2026-11-12] 서버 로그의 경고 메시지를 끝까지 읽어야 한다

**Trigger**: `npm run dev`를 여러 번 "재시작"했다고 생각했는데, 실제로는 Next.js가 매번
`⨯ Another next dev server is already running... PID: XXXXX`라고 경고하고 있었다. 이
경고를 못 보고 지나쳐서, `next.config.ts` 수정이 실제로는 몇 번이나 적용이 안 된 채로
계속 같은(오래된) 프로세스를 테스트하고 있었다.
**Pattern**: 명령 실행 후 "원하는 결과(포트가 응답함)"만 확인하고 로그 전체를 읽지
않았다. 중간에 낀 경고/에러 메시지를 건너뛰고 "성공"으로 넘어간 것.
**Rule**: 서버를 띄우는 명령을 실행하면, 단순히 "응답하는지"만 보지 말고 **로그 전체를
한 번은 훑어서 경고(⚠)·에러(⨯) 표시가 있는지 확인**한다. 특히 "재시작"이 의도인데 "이미
실행 중"이라는 메시지가 보이면, 포트가 응답한다고 해서 새 설정이 반영됐다고 믿으면 안
된다 — PID를 직접 확인하고 필요하면 `kill -9 <PID>`로 확실하게 끝낸다.
**Files affected**: 서버·데몬을 재시작하는 모든 작업. `lsof -ti:PORT | xargs kill`이
항상 실제 리스닝 프로세스를 잡는다고 가정하지 말 것 — 이번처럼 다른 프로세스가 포트를
먼저 점유해버리면 무용지물이다.

## [2026-11-12] 제목 키워드로 장르를 보강할 땐 이미 정확한 분류를 덮어쓰지 않는지
재분류 전후 분포를 꼭 비교한다

**Trigger**: "미분류"였던 "정승환 콘서트"를 "콘서트"로 구제하려고 제목에 "콘서트"
키워드 규칙을 추가했는데, 이걸 KOPIS가 이미 장르를 정확히 알고 있는 매칭 공연에도
똑같이 적용해버려서 "OOO 신년 콘서트"처럼 KOPIS가 "클래식"으로 정확히 분류해둔
공연까지 일반 "콘서트"로 덮어썼다(클래식 18건→9건, 뮤지컬 29→26, 스포츠/기타
20→19로 줄어드는 걸 재분류 직후 로그로 발견해서 배포 전에 잡음).
**Pattern**: "A가 미분류인 게 문제다 → A를 제목 키워드로 구제하는 규칙을 추가한다"에서
멈추고, 그 규칙이 "이미 신뢰할 수 있는 값을 가진 다른 행들"에도 똑같이 적용된다는
걸 놓쳤다. 매칭 함수가 우선순위 리스트(`GENRE_KEYWORDS_BY_TITLE`)를 모든 행에
무조건 먼저 적용하는 구조였다는 걸 확인 안 하고 그 리스트에 바로 추가했다.
**Rule**: 분류/매칭 규칙에 새 조건을 추가할 때는 (1) 그 규칙이 **어떤 행 전체에
적용되는지(조건 없이 전체? 특정 조건에서만?)** 먼저 확인하고, 필요하면 "이미 신뢰
가능한 값이 있는 경우엔 적용 안 함"으로 범위를 좁힌다. (2) 규칙 추가 후에는 영향받은
쪽(새로 구제된 것)만 보지 말고 **다른 카테고리들의 건수가 그대로인지(의도치 않게
줄어들지 않았는지)**까지 재실행 로그로 비교한다.

## [2026-11-14] "로컬에서 완성"과 "배포 가능"은 다르다 — git 미반영 파일이 배포 사이트를 깼음

**Trigger**: 사용자가 QR로 실제 배포 사이트를 열어보고 "로고가 깨진다"고 지적. 확인해보니
9단계(디자인 다듬기)에서 이미 로컬 작업 디렉터리에 만들어 README·CLAUDE.md에도
"완료"로 기록해둔 로고 파일(`frontend/public/olympic-park-mark.png`)이 **한 번도
git에 커밋된 적이 없어서** Vercel 빌드에는 아예 없었고, 이를 참조하는 `layout.tsx`
코드는 이미 커밋·배포돼 있어 404(깨진 이미지)로 나타났다.
**Pattern**: "로컬 `npm run build`·`npm run lint`가 통과했다 = 배포해도 똑같이
동작한다"고 암묵적으로 가정했다. 로컬 작업 디렉터리에는 커밋 여부와 무관하게 모든
파일이 존재하기 때문에, 빌드·린트 성공은 "지금 디스크에 있는 파일 기준"일 뿐
"git에 커밋된 파일 기준"이 아니라는 차이를 놓쳤다. 이전에도 비슷한 패턴이 있었다
(8단계 블로커 2: `.gitignore`가 `data/processed/*`를 무시해서 배포하면 빈 화면가
뜨는 문제) — 그때는 미리 발견해서 고쳤지만, 이번엔 다른 디렉터리(9단계 작업분)에서
같은 종류의 문제가 또 생겼는데 사전에 체크하지 않았다.
**Rule**: 배포(push) 전에는 반드시 `git status`로 **untracked·modified 파일 목록
전체**를 보고, 배포된 코드가 참조하는 파일(이미지·데이터 파일 등 정적 자산 포함)이
전부 커밋 대상에 들어있는지 확인한다. 특히 "이전 세션에서 완료했다고 기록했지만
커밋 여부를 확인 안 한 작업"이 있다면, 그 작업에서 새로 추가한 파일(새 이미지,
새 데이터 파일 등)이 git에 실제로 들어있는지부터 점검— 로컬 빌드 성공은 이 점검을
대체하지 못한다.
**Files affected**: 배포 직전 체크리스트 전반(`tasks/todo.md` "8단계: 배포"), 특히
정적 자산(이미지 등)을 추가하는 모든 프론트엔드 작업. 커밋되지 않은 작업이 있다면
배포 전에 `git status`로 먼저 드러내고, 배포에 필요한 파일인지 판단해서 포함 여부를
결정한다.

## [2026-11-14] "앱을 다운로드/설치"처럼 모호한 요청은 구현 방식이 여러 갈래임을 먼저 확인

**Trigger**: "QR코드 만들어서 모바일로 앱 다운로드해서 쓸 수 있게 하고 싶어"라는 요청을
받고 처음엔 "QR 코드를 만들어서 → 접속하면 브라우저 메뉴에서 홈 화면에 추가하는 법을
안내하는 페이지"로 구현했는데, 사용자가 "너가 잘못 이해한 것 같아. QR을 스캔해서
모바일에 앱을 설치할 수 있도록 만들고 싶은거야"라고 정정 — 실제로 원한 건 "사이트에
들어가면 설치 버튼이 바로 뜨는" 경험이었음.
**Pattern**: "앱을 다운로드/설치해서 쓰고 싶다"는 문장 하나가 최소 3가지 완전히 다른
구현(① 수동 안내 문서, ② 사이트에서 바로 뜨는 설치 버튼(PWA `beforeinstallprompt`),
③ 진짜 네이티브 앱 배포)으로 갈릴 수 있는데, 그 중 가장 작업량이 적은 해석(①)을
먼저 시도하고 승인을 구했다가, 사용자가 실제로 원한 건 더 구체적인 UX(②)였다. 질문을
하긴 했지만("PWA vs 네이티브 앱") 선택지 안에 "그 PWA를 어떻게 노출할 것인가"(버튼 vs
안내문)까지는 포함을 안 해서, 승인받은 답이 실제 기대와 어긋났다.
**Rule**: 사용자가 "설치/다운로드해서 쓰고 싶다" 같은 최종 사용자 경험을 말로
설명하면, 구현 옵션을 제시할 때 **그 경험이 화면에서 실제로 어떻게 보이는지**
(버튼이 바로 뜨는지, 안내문만 있는지, 몇 번 눌러야 하는지)까지 선택지에 명시해서
확인받는다. "기술 방식"(PWA vs 네이티브)만 묻고 "노출 방식"(자동 버튼 vs 수동 안내)은
내가 임의로 더 쉬운 쪽을 골라서 넘어가지 않는다.
**Files affected**: 사용자 경험(UX)을 다루는 모든 기능 요청 — 특히 "앱처럼",
"설치", "다운로드" 같은 플랫폼 중립적 표현이 들어간 요청은 구현 전에 화면 단위로
재확인할 것.
